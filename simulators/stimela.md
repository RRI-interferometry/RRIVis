Stimela 2 is a workflow-management framework for radio interferometry data
processing. It orchestrates "cabs" (atomic, parameter-typed processing tasks)
into "recipes" (DAGs of steps with aliasing, looping, scatter, conditionals)
and dispatches them through pluggable backends (native, Singularity, Kube,
optionally wrapped by SLURM). Containerised execution via Docker or Podman is
present as scaffolding only — see §11.

The two-package split is intentional: **scabha** owns parameters, schemas,
`Cargo`, `SubstitutionNS`, and `configuratt` config loading; **stimela** owns
the workflow shell (Cab, Recipe, Step, backends, CLI, display, logging).
`stimela/exceptions.py` re-exports the scabha exception classes so callers
have a single import surface.

## 5. Public CLI

The CLI is defined as a single `click.Group` in `stimela/main.py`. The group
is a custom `RunExecGroup` (lines 27-46) that aliases `exec → run` and
`help → doc`. All subcommands live under `stimela.commands.*`.

```
stimela [GLOBAL OPTIONS] SUBCOMMAND [SUBCOMMAND OPTIONS] ARGS...
```

### 5.3 Legacy / dormant subcommands

These remain in the source tree but are **not** registered with the click group
in `main.py`. They use the old argparse `make_parser(subparsers)` API and
their `func()` bodies are no-ops or stubs. From `main.py:168-176` (verbatim):

> `## These one needs to be reimplemented, current backed auto-pulls and auto-builds: images, pull, build, clean`
> `## this one is deprecated, stimela doc does the trick: cabs`
> `## the ones below should be deprecated, since we don't do async containers anymore: containers, kill, ps`

So `stimela cabs|pull|push|images|kill|ps|containers` are **not callable** in
2.x; the documentation is here purely so users grepping the code don't get
confused.

### 5.4 `stimela run` in detail (`commands/run.py:195-731`)

`stimela run [OPTIONS] PARAMETERS...`

`PARAMETERS...` is a positional list that can intermix any of:

* `filename.yml` — YAML config or recipe file
* `(module.path)foo.yml` or `module::foo.yml` — file resolved relative to a
  Python package's directory (`resolve_recipe_files`, line 35-109). Wildcards
  permitted, and a directory may contain a `MANIFEST.stimela`.
* `RECIPE_NAME` or `CAB_NAME` — selects which recipe/cab to run
* `param=value` — recipe/cab input assignment (parsed via `yaml.safe_load`,
  `=UNSET` is the special UNSET sentinel)
* `section.subsection.key=value` — equivalent to `-c`/`--config`

Options:

| Flag | Effect |
|---|---|
| `-s, --step STEP[,STEP][:STEP]` | Run only specific steps; ranges with `BEGIN:END`. Implies `--enable-step` |
| `-k, --skip-step STEP[,…]` | Force-skip specific steps |
| `-t, --tags TAG[,…]` | Run only steps with these tags (and `always`) |
| `--skip-tags TAG[,…]` | Skip steps with these tags |
| `-e, --enable-step STEP[,…]` | Force-run steps that are normally skipped |
| `-f, --disable-fresh-skips` | Override `skip_if_outputs: fresh` |
| `-F, --disable-exist-skips` | Override `skip_if_outputs: exist` |
| `-c, --config X.Y.Z=VALUE` | Set arbitrary config dotlist value |
| `-a, --assign PARAM VALUE` | Two-arg form of `param=value` |
| `-C, --config-assign X.Y.Z VALUE` | Two-arg form of `-c` |
| `-l, --last-recipe` | If multiple recipes, pick the last one |
| `-d, --dry-run` | Pre-validate, then exit without executing |
| `-p, --profile DEPTH` | Print per-step profiling stats to a depth |
| `-N, --native` | Shortcut for `-C opts.backend.select=native` |
| `-S, --singularity` | Shortcut for `-C opts.backend.select=singularity` |
| `-K, --kube` | Shortcut for `-C opts.backend.select=kube` |
| `--slurm` | Shortcut for `-C backend.slurm.enable=True` |
| `-dc, --dump-config` | Dump effective config to `stimela.recipe.config.yaml` in log dir |
| `-pf, --parameter-file FILE` | Use parameter values from a YAML file (lower precedence than `param=value`) |

The runner:

1. Loads and parses the user-provided files via `load_recipe_files` (line 112).
   Top-level keys that already exist in the global config (e.g. `cabs`, `opts`,
   `lib`) are merged into `stimela.CONFIG`. Other top-level dict keys are
   treated as recipe definitions and inserted into `lib.recipes`. The special
   key `DEFAULT: <name>` chooses the default runnable.
2. Picks a recipe or cab by command-line argument, single-recipe heuristic,
   `-l`, or `DEFAULT` (`run.py:478-518`).
3. Builds an outer `Step(recipe=...)` or `Step(cab=...)` and `prevalidate()`s
   it (`run.py:597-608`).
4. Builds a DAG via `recipe.to_dag()`, applies `RunConstraints`
   (`graph_to_constraints` in `kitchen/run_state.py:graph_to_constraints`) for
   tag/step inclusion/exclusion, then `recipe.restrict_steps(constraints)`.
5. Executes `outer_step.run(is_outer_step=True, subst=subst)`.
6. Closes backends, saves profiling stats, flushes accumulated warnings.

### 5.5 `stimela build`

`commands/build.py` is a thin wrapper that calls `run.callback(...,
build=True)`. It accepts a subset of `run`'s flags (`--rebuild`, `--all-steps`,
step/tag filters, backend selectors). Only the singularity backend has a
`build()` method (`backends/singularity.py`).

### 5.6 `stimela doc`

`commands/doc.py` walks YAML files and uses `Recipe.rich_help` / `Cab.rich_help`
(implemented in scabha's `Cargo`) to print a tree to the console. Detail
levels via `-A/-O/-I/-R` map to `ParameterCategory.{Hidden,Obscure,Implicit,
Required}`. Fnmatch is used to match recipe/cab name patterns.

### 5.7 `stimela cleanup`

Loads recipes, then for each backend listed in `opts.backend.select` calls
that backend's `cleanup()` function (e.g. `kube.cleanup` removes residual PVCs
and pods).

### 5.8 `stimela config`

Either prints `opts.*` if no args, or applies `KEY=VALUE` settings, then saves
the config file. `--local`, `--virtual-env`, `--user` choose the destination
file from `CONFIG_LOCATIONS` (see §7).

## 7. Configuration model

### 7.1 Loading order (`stimela/config.py:85-92, 195-201`)

`CONFIG_LOCATIONS` is an `OrderedDict` of well-known files that are loaded in
this order:

| Key | Path |
|---|---|
| `package` | `<install>/stimela/stimela.conf` (always present) |
| `local` | `./stimela.conf` |
| `venv` | `$VIRTUAL_ENV/stimela.conf` (if venv active) |
| `stimela` | `~/.stimela/stimela.conf` (if dir exists) |

Each config file is merged via `OmegaConf.unsafe_merge`. Then any `-c FILE`

cached in `~/.cache/stimela-configs` (key includes path list + dotlist).

### 7.2 Top-level structured schema (`config.py:175-189`)

## 8. Backends

### 8.1 Selection logic

`StimelaBackendOptions` (`backends/__init__.py:46-104`) carries:

* `default_registry`: `quay.io/stimela2`
* `override_registries`: `Dict[str, str]` (use a pull-through cache)
* `select`: comma-separated list (default `"singularity,native"`); the
  first available backend wins
* `variety`: optional named pre-set from `opts.backend_varieties`
* per-backend sub-configs: `singularity`, `kube`, `native`, `slurm`,
  `docker` (placeholder)
* `rlimits`: `Dict[str, Any]` — passed to `setrlimit` via
  `native/run_native.py:update_rlimits`
* `verbose`: int — extra backend-selection logging

`validate_backend_settings()` in `runner.py:45-108` walks `select`, queries
each backend's `is_available(opts)`, accommodates the `requires_container_image`
flag (skips backends that need an image when the cab declares none), and
returns a `BackendRunner` dataclass with `run()` and `build()` methods that
delegate to the chosen backend module's free functions.

### 8.2 Native backend (`backends/native/`)

* Always available (`is_available` returns `True`).
* `NativeBackendOptions(enable=True, virtual_env: Optional[str]=None)`.
* `run_native.run` flow:
  1. `update_rlimits(backend.rlimits, log)` — sets `RLIMIT_*`.
  2. Optional virtual-env activation (`source $venv/bin/activate`).
  3. `cab.flavour.get_arguments(...)` builds `(args, log_args)`.
  4. Optional slurm `wrap_run_command` to prepend `srun ...`.
  5. `xrun(args[0], args[1:], shell=False, output_wrangler=cabstat.apply_wranglers, ...)` from `utils/xrun_asyncio.py`.
  6. Returns a `Cab.RuntimeStatus` (`success/errors/warnings/outputs`).

### 8.3 Singularity backend (`backends/singularity.py`)

* `SingularityBackendOptions` — `enable`, `image_dir=~/.singularity`,
  `auto_build`, `rebuild`, `executable`, `remote_only`,
  `contain`/`containall`, `bind_tmp`, `clean_tmp`, `bind_dirs` (typed
  `BindDir` dict with `host/target/mode/mkdir/conditional`), `env`,
  `ephemeral`.
* Detects the `singularity` binary via `shutil.which`, caches the version.
* Mounts the host paths derived from cab parameters (using
  `backends/utils.py:resolve_required_mounts` — symlink-aware, `URI`-aware,
  uses `path_policies.access_parent`/`write_parent` to optionally bind parent
  directories).
* `requires_container_image = True`: cabs without `image:` are routed to a
  different backend in the `select` list (often `native`).
* Implements both `build()` (auto-pull from registry to `image_dir`) and
  `run()` (build the `singularity exec --bind ... --contain ...` argv). The
  full file is ~900 LoC.

### 8.4 Kubernetes backend (`backends/kube/`)

* `requires_container_image = True`.
* `KubeBackendOptions` (`__init__.py:69-227`) is the most elaborate config in
  the project: `infrastructure` (startup/exit policies, PVC reporting),
  `volumes: Dict[str, KubeBackendOptions.Volume]` (with capacity, storage
  class, access modes, lifecycle, init commands, snapshot source, exist
  policy), `dask_cluster` (`KubeBackendOptions.DaskCluster` for distributed
  jobs), `service_account`, `kubectl_path`, `env`, `dir` (working dir inside
  pod), `provisioning_timeout`, `connection_timeout`, `always_pull_images`,
  `debug` (verbose, `pause_on_start`, `save_spec`, `log_events`,
  `event_format`), `job_pod` (KubePodSpec), `user` (UserInfo with NSS
  injection), `predefined_pod_specs`.
* Module structure:
  * `infrastructure.py` (398 LoC) — cluster init/close/cleanup, PVC mgmt
  * `pod_proxy.py` (402 LoC) — single-pod execution proxy
  * `run_kube.py` (625 LoC) — main entry point for kube cab execution
  * `daskjob.py` (296 LoC) — Dask cluster CR scheduling
  * `run_daskjob.py` (110 LoC) — invocation inside Dask worker
  * `kube_utils.py` (298 LoC) — name sanitisation, label helpers
* Uses `kubernetes.client` (CoreV1Api, CustomObjectsApi) with a kubeconfig
  loaded via `kubernetes.config.load_kube_config(context=...)`. Honours
  `_kube_context` invariance — once chosen, cannot change mid-run.
* Resource labels include `stimela_user`, `stimela_session_id` (random hex),
  enabling per-session pod cleanup.

### 8.5 SLURM (wrapper, not a backend)

`backends/slurm.py:SlurmOptions`. SLURM is **not** in the
`Backend` enum (which is just `singularity kube native`); instead, when
`opts.backend.slurm.enable=True`, the chosen native or singularity backend's
command line is wrapped with `srun [opts...] [slurm_runner.sh ...] -- args`.

* `srun_path` — auto-discovered via `which("srun")` if unset
* `srun_opts: Dict[str, str]` — passed as `--key value` (underscores → dashes)
* `srun_opts_build` — separate options for image builds; falls back to
  `srun_opts` if unset
* `build_local: bool=True` — image builds run on the head node by default
* `wrap_run_command` and `wrap_build_command` produce `(args, log_args)` tuples

`slurm_runner.sh` is a shell wrapper used when ephemeral binds are required
(it parses `name::basedir` arguments before `--`).

### 8.6 Docker / Podman (stubs)

* `docker.py` — `is_available` returns `False`, `get_status` returns
  `"not implemented"`. `requires_container_image=True`.
* `podman.py` — older code from the 1.x era; `is_available` returns `False`.

The `Backend` enum at `backends/__init__.py:20` excludes both, so they are
unreachable from the CLI in 2.x. The author left a memo to self at line 19:

```
# Backend = Enum("Backend", "docker singularity podman kubernetes native", module=__name__)
Backend = Enum("Backend", "singularity kube native", module=__name__)
```

### 8.7 Cab flavours (`backends/flavours/`)

A "flavour" is the strategy for actually invoking a cab's `command`. There are
four registered flavours (`flavours/__init__.py:91-96`):

| Kind | Class | File | Behaviour |
|---|---|---|---|
| `binary` (default) | `BinaryFlavour` | `binary.py` | shlex-split `command`, append `args`, append generated argument list. Uses `default-python` image if cab has none. |
| `python` | `PythonCallableFlavour` | `python_flavours.py` | `cab.command = module.path.func`; serialises a Python invocation (with `repr` for kwargs) and passes it through `python -c ...` — supports `output: NAME` (single named output) or `output_dict: True` (function returns a dict). |
| `python-code` | `PythonCodeFlavour` | `python_flavours.py` | The `command` itself is treated as a chunk of Python source, base64+zlib-encoded into a one-liner. Supports `pre_commands` and `post_commands` ordered dicts. |
| `casa-task` | `CasaTaskFlavour` | `casa.py` | Wraps the call into a CASA task: `xvfb-run -a casa --log2term ... -c "task(**params)"`. Adds a wrangler that maps `SEVERE` lines (excluding `MeasTable::dUTC`) to errors. |

Adding a new flavour: subclass `_BaseFlavour` (or `_CallableFlavour`),
register it in `flavours/__init__.py:lookup_flavour._flavour_map`. Each
flavour's `get_arguments(cab, params, subst, virtual_env, check_executable,
log) -> (full_args, abbreviated_args_for_logging)` is the contract.

## 9. Core concepts (recipe / cab schemas)

### 9.1 Cab schema (dataclass `Cab` in `kitchen/cab.py:75-409`)

Cab inherits from `scabha.cargo.Cargo`, which provides `inputs`, `outputs`,
`defaults`, `aliases`, `info`, `dynamic_schema` etc. Stimela-specific fields:

| Field | Type / default | Meaning |
|---|---|---|
| `image` | `Optional[Any]` (str or `ImageInfo` dict) | Container image. If `None`, runs natively. Strings are parsed by `ImageInfo.from_string` (`registry/name:version`). |
| `command` | `str` (MISSING by default) | Shell command, Python callable dotted path, or Python source — depending on `flavour`. Subject to `{}`-substitution (`build_command_line`, line 196-212). |
| `args` | `List[str]` | Extra args inserted before the auto-generated argument list. |
| `flavour` | `Optional[Any]` | Either a string (`binary`/`python`/`python-code`/`casa-task`) or a mapping with a `kind` field. |
| `backend` | `Optional[Dict[str, Any]]` | Per-cab backend overrides; merged with `StimelaBackendSchema`. |
| `parameter_passing` | `args` (default) or `yaml` | `args` builds CLI arguments; `yaml` dumps the param dict to a single YAML string. |
| `management` | `CabManagement` | Sub-fields: `environment` (env dict), `cleanup`, `wranglers` (dict of regex→action). |
| `policies` | `ParameterPolicies` (from scabha) | Default conversion policies; per-parameter overrides win. |

Argument-building (`Cab.build_argument_list`, lines 250-406) honours these
policies:

* `prefix` — default `--`
* `key_value` — produces `--opt=val`
* `nom_de_guerre` — alternate command-line name
* `repeat` — list-handling: `list`, `[]`, `repeat`, or any string separator
* `format`, `format_list`, `format_list_scalar`, `split`
* `replace` — name-rewrite map applied per-parameter
* `positional`, `positional_head`
* `explicit_true`, `explicit_false` — for booleans
* `skip`, `skip_implicits`, `pass_missing_as_none` — control which params
  reach the command line.

`Cab.RuntimeStatus` (lines 411-474) keeps `_success`, `_errors`,
`_warnings`, `_outputs`, plus `apply_wranglers(output, severity)` which is
plugged into `xrun`'s line callback.

### 9.2 Recipe schema (`kitchen/recipe.py:72-...`)

```
@dataclass
class Recipe(Cargo):
    steps:           Dict[str, Step]                # OrderedDict in practice
    assign:          Dict[str, Any]                 # variable assignments
    assign_based_on: Dict[str, Any]                 # conditional assignments
    aliases:         Dict[str, Any]                 # name → list of "step.param" targets
    backend:         Optional[Dict[str, Any]]       # backend overrides
    for_loop:        Optional[ForLoopClause]        # if set, recipe is a loop
```

`Cargo` adds `name`, `info`, `inputs: Dict[str, Parameter]`,
`outputs: Dict[str, Parameter]`, `defaults`, `dynamic_schema`. Recipe
finalisation:

1. `__post_init__` flattens nested `aliases`/`assign` dicts via
   `flatten_param_dict`, builds `Step` objects from raw dict configs, validates
   alias syntax (`name → "step.param"`, `(cabkind).param`, wildcards `*?[`).
2. `finalize(config, log, name, fqname, backend, nesting)` (line 643+) creates
   per-step loggers, recurses into sub-recipes, builds `_alias_map` and
   `_alias_list`, and copies parameter schemas through aliases.
3. `prevalidate()` (in `step.py`) runs scabha's typed validation, propagates
   alias values upward and downward, evaluates `assign`/`assign_based_on`
   under `SubstitutionNS`.

### 9.3 `ForLoopClause` (`recipe.py:51-65`)

```
var: str                                # iterant name
over: Optional[Any]                     # input name OR a literal list
scatter: int = 0                        # parallel scatter; -1 = unlimited workers
display_status: Optional[str]           # status-bar format
output_elements: Dict[str, Any]         # expressions accumulated into list outputs
```

`scatter != 0` switches the loop to `concurrent.futures.ProcessPoolExecutor`
parallel execution (`Recipe._loop_pool`).

### 9.4 Step schema (`kitchen/step.py:82-...`)

```
@dataclass
class Step:
    cab:    Optional[Any]                # cab name (mutually exclusive with recipe)
    recipe: Optional[Any]                # nested recipe name or Recipe
    params: Dict[str, Any]               # parameter assignments
    info:   Optional[str]                # comment string
    skip:   Optional[str]                # bool / formula evaluating to bool
    skip_if_outputs: Optional[str]       # 'exist' or 'fresh'
    tags:   List[str]
    name:   str                          # internal label
    fqname: str                          # recipe.label or recipe.label.label
    assign: Dict[str, Any]
    assign_based_on: Dict[str, Any]
    backend: Optional[Dict[str, Any]]
    preamble: Dict[str, Any]             # expressions evaluated before run
    epilogue: Dict[str, Any]             # expressions evaluated after run
```

Skip is a string formula evaluated per iteration; `True/true/1`,
`False/false/0/""/None` get pre-computed at `__post_init__`. `skip_if_outputs`
implements Make-like behaviour:

* `exist`: skip if all outputs exist
* `fresh`: skip if outputs exist *and* are newer than all inputs

Both can be globally overridden by `--disable-fresh-skips` /
`--disable-exist-skips` (see CLI table). Per-step backend selection cascades
config → recipe → step (`apply_backend_varieties` merges `opts.backend_varieties[X]`
on top).

### 9.5 Aliases (cf. `tests/test_aliasing.yml`)

```yaml
aliases:
  a: [s1.a, s2.a]                       # propagate the same value to two steps
  b: [s1.b, s2.b]
  out: [s4.out]                         # output alias (one step only)
  e: ['s[12].e']                        # fnmatch wildcard over step names
  f: ['(echo).f']                       # all steps using cab "echo"
  g: ['xx*.g']                          # match any unfound step (no-op)
```

Multiple input targets must share `dtype` (enforced in `_add_alias`,
`recipe.py:564-572`). Output aliases must be 1:1. Implicit inputs cannot be
aliased (line 547-552).

### 9.6 `assign` and `assign_based_on`

```yaml
assign:
  dir-out: '{recipe.dirs.base}/{recipe.dirs.sub}{recipe.output-suffix}'
  log.dir: '{recipe.dir-out}/logs/log-{config.run.datetime}'
assign_based_on:
  band:                                  # base variable
    L:                                   # case
      var1: x
      config.cabs.wsclean.inputs.dummy.default: 1000
    UHF:
      var1: x1
    DEFAULT:                             # fallback
      var1: x_default
```

Assignments are re-evaluated *at every step*, so substitutions like
`{info.suffix}` change with the active step's label suffix
(`docs/source/fundamentals/anatomy.rst:128`). Assign keys may target nested
namespaces — `config.x.y`, `log.dir`, `step.param`, etc. Implementation:
`Recipe.update_assignments` (`recipe.py:171-302`).

### 9.7 Substitutions (`scabha.substitutions.SubstitutionNS`)

Stimela populates a substitution namespace with at least:

| Key | Source |
|---|---|
| `config` | The active `OmegaConf` config (`stimela.CONFIG`) |
| `recipe` | Current recipe's parameters + assigned vars |
| `previous` | Last sibling step's parameters/outputs |
| `steps.<label>` | Any sibling step's parameters/outputs |
| `current` | The current step's params (`commands/run.py:528`) |
| `info` | `fqname`, `label`, `label_parts`, `suffix`, `taskname` |
| `self` | Alias for `info` (`run.py:526`) |

Two flavours of expansion exist: braced `"{recipe.dir-out}/foo.fits"` for
plain string formatting, and `=`-prefixed formulas
`"=STRIPEXT(current.cube) + '.pbcorr.fits'"` evaluated by
`scabha.evaluator`.

### 9.8 Wranglers (`kitchen/wranglers.py`)

A wrangler is a regex → action pair declared in
`management.wranglers`. They are applied to each line of cab output (in
`Cab.RuntimeStatus.apply_wranglers`). Built-in actions:

| Specifier | Action |
|---|---|
| `REPLACE:repl` | `re.sub(pattern, repl, output)` |
| `HIGHLIGHT:style` | wrap in rich markup `[style]…[/style]` |
| `SEVERITY:LEVEL` | force log level (`ERROR`/`WARNING`/`INFO`/`DEBUG`/`CRITICAL`/`FATAL`) |
| `SUPPRESS` | drop the line from log |
| `WARNING:msg` | record a deferred warning, log line at WARNING |
| `ERROR[:msg]` | mark cab as failed, log line at ERROR with red markup |
| `DECLARE_SUCCESS` | mark cab as succeeded even on non-zero exit |
| `PARSE_OUTPUT:[name]:group:dtype` | parse a regex group as `str/bool/int/float/complex/json/yaml` and store it as a named output |
| `PARSE_JSON_OUTPUTS` | use named regex groups and `json.loads` each one |
| `PARSE_JSON_OUTPUT_DICT` | parse first regex group as a JSON dict of outputs |

Class registration is automatic — `all_wranglers` is built at import time
(`wranglers.py:312-316`) by introspecting subclasses of `_BaseWrangler`.

### 9.9 Step/tag selection (`run_state.py`)

`graph_to_constraints(graph, tag_inclusions, tag_exclusions, step_inclusions,
step_exclusions, step_unskips) -> RunConstraints`. The 4-level hierarchy
(`STATUS_HIERARCHY = ("disabled", "enabled", "weakly_disabled",
"weakly_enabled")`) lets a tag's `always`/`never` be overridden by an
explicit step inclusion. The `:` syntax in `--step` selects a range of
sibling steps; nested-recipe steps are addressed as
`outer-step.sub-recipe.step`.

## 13. Notable internals

* **scabha is not vendored** — it's a git pin (`93b61c1`) of
  `caracal-pipeline/scabha`. The README's `pyproject.toml` has a comment "Remove
  when divorce is complete", suggesting an in-progress refactor.
* **Substitution evaluation** uses `scabha.evaluator.Evaluator` and is sensitive
  to circular references (issue 527 in tests). Self-referencing formulas raise
  `CyclicSubstitutionError`.
* **OmegaConf structured configs** are pervasive: every dataclass becomes a
  schema via `OmegaConf.structured(cls)`. Pre-validation against
  `RecipeSchema`/`StepSchema`/`CabSchema`/`StimelaBackendSchema` happens at
  several points; merges use `OmegaConf.unsafe_merge` (faster, no copy) for
  speed.
* **Logging** centralises through `stimelogging.logger()`. Custom
  `StimelaConsoleHander(rich.logging.RichHandler)` understands `FunkyMessage`
  pairs (markup vs. boring), and `update_file_logger` adds nested per-step
  log files using the substitution namespace.
* **Process management** uses `utils/xrun_asyncio.py` (216 LoC) — an asyncio
  subprocess driver that streams stdout/stderr line by line through the
  output-wrangler callback, supports `gentle_ctrl_c` (forwards SIGINT once,
  then SIGTERM, then SIGKILL), and returns the exit code. The legacy
  `utils/xrun_poll.py` is kept for the `schedulers/slurm.py` legacy path
  (`SlurmBatch`).
* **Run datetime / env** — the `config.run` dict is populated each time
  `load_config` is called (`config.py:294-308`): `date`, `time`, `datetime`,
  `ncpu`, `ncpu-logical`, `ncpu-physical`, `node`, `hostname`, `env`
  (with `${...}` escaped to `\${...}` so substitutions don't recurse
  through environment variables).
* **Cache** — full configs are cached in `~/.cache/stimela-configs`; clear
  with `stimela -C` / `--clear-cache`.

## 14. Known limitations / stubs / TODOs

* **Docker and Podman backends are stubs** (`backends/docker.py`,
  `backends/podman.py`); only `singularity`, `kube`, `native` are wired up.
* **Subcommands `cabs`, `pull`, `push`, `images`, `kill`, `ps`, `containers`
  remain in the source tree but are not registered with the click CLI**
  (`main.py:168-176` explicitly notes deprecation). Their bodies are no-ops.
* **`stimela[kube]` extra is referenced in error messages**
  (`backends/kube/__init__.py:34`) **but is not declared** in
  `pyproject.toml` — install `kubernetes` Python package manually.
* **`DEVNOTES.md` calls out two unresolved design problems**:
  1. *Globs* — `prevalidate()` must expand globs but expanded values lose
     their "this is a glob" identity, complicating re-evaluation in
     `validate_outputs()`. The author proposes either tagging values with an
     explicit `glob:` prefix or keeping a side-copy of original params in
     `Cargo`.
  2. *Aliases* — the propagation rules (recipe→step, step→recipe, and
     during/after running) are evolving; see `DEVNOTES.md:24-62` for the
     intended state machine.
* **Build steps for non-singularity backends** — only singularity has a real
  `build()`; the kube backend pulls images at run time, the native backend
  has no notion of build.
* **`scabha` divorce** — the project intends to inline scabha eventually.
  Direct imports across the boundary are pervasive, so consumers should
  pin both packages together.
* **CHANGES.md is stale** — entries stop at `1.2.0` even though the package
  is at 2.2.0rc0; users should consult git log and GitHub releases.

## 15. Quick command reference (cheat sheet)

```bash
# Run a recipe
stimela run recipe.yml RECIPE_NAME [param=value ...]
stimela exec recipe.yml RECIPE_NAME ...     # alias for run

# Run with a backend selection or wrapper
stimela -b native run ...
stimela -b singularity run ...
stimela -b kube run ...
stimela run --slurm recipe.yml ...

# Selective execution
stimela run recipe.yml -s step1,step2
stimela run recipe.yml -s step1:step5      # range
stimela run recipe.yml -t imaging          # tag selection
stimela run recipe.yml --skip-tags slow

# Build singularity images for a recipe
stimela build recipe.yml [-r] [-a] [recipe-name]

# Documentation
stimela doc recipe.yml [pattern] [-A|-O|-I|-R] [-l]

# Configuration
stimela config                                  # print opts
stimela config foo=bar --user                   # write ~/.config/stimela.conf
stimela cleanup recipe.yml                      # backend-specific cleanup

# Global niceties
stimela -v -B run ...                           # verbose, no rich
stimela -C run ...                              # clear config cache first
stimela -dc run recipe.yml                      # dump effective config to log dir
stimela run -d recipe.yml                       # dry run (validate only)
```
